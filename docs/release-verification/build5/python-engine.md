## Build and installation boundary

[Exact project source/build instructions](../../source-and-build.md) and [PDF maintenance](../../pdf-maintenance.md) describe the selected manifest, App build, runtime installation and pin update entry points. The current source archive contains the installer, manager/translator integration, bridge, compatibility adapter, inventory checker, manifest, notices, bundled modified inputs and build scripts. This review hashes those current inputs in the machine record. The historical `project-adaptations/` copies of **`runtime_inventory.py` and `PDFRuntimeInstaller.swift` differ from build 5**; use the exact project source archive for these files. The current bridge, compatibility and translator copies still match their origin counterparts. Do not reconstruct the current App by blindly using every historical adaptation copy.

The current installer reads/validates the manifest, checks bundled or HTTPS input sizes/hashes, unpacks CPython, installs only the selected wheels with `pip --no-index --no-deps --no-compile`, copies assets, runs health/inventory logic and verifies the resulting inventory. This is an inspected implementation association. The health script checks interpreter/package versions and imports, including an ONNX session; version alone does not distinguish the BabelDOC derivative, so exact wheel/module/inventory hashes remain necessary. No runtime was imported or installed for this review.

`current/fonts/wheel/README.zh-CN.md` gives the concrete modified-wheel build command, original wheel digest, patch/source paths and fixed ZIP procedure. `independent-wheel-validation.json` records two historical byte-identical outputs with the same input/Python/zlib conditions, 351 original unchanged members, four changed members and one added notice. This review rechecked the delivered wheel and patches; it did **not** rerun that build. Historical `current/fonts/evidence/registry-test-results.json` and `final-evidence-review.json` cover 34-font cache lookup, six-language/four-style registry mapping and four missing/corrupt negative cases under their stated offline scope. Font rendering/shaping evidence is #5's scope, and these focused results are not a full PDF translation/App acceptance pass.

For a modified component, use a separate development output/runtime, rebuild the affected component using its supplied source/build entry points, update its manifest identity/hashes and bundled index as applicable, then build the modified App with [the documented build script](../../source-and-build.md). The maintenance lock tool writes a new output and may query public metadata; it is not a bit-identical native rebuilder. The archive's `origin-materials/2026-10-26/third-party/BUILDING.md` explicitly leaves the **end-to-end modified-component replacement/rebuild/install procedure untested**. No instruction here authorizes overwriting a live managed runtime, bypassing inventory checks or changing security settings.
